# 下一步优化与开发方案

## 1. 现状回顾与问题定义
用户已在本地验证：
- 核心服务已全部正常启动，并成功注册进 Nacos（包括 Gateway, Auth, Admin, Game, Social, Monitor, Job 等）。
- 数据库与 Redis 均已正常连接。

目前处于 **P1 平台通信完全跑通，但业务层大多处于 Mock 阶段** 的状态。下一步的目标是逐步将公共中间件能力落地到真实的业务场景中。

## 2. 备选优化路线对比 (方案脑暴)

### 方案 A：纯粹的业务 CRUD 补全（侧重数据库）
- **实现内容**：在 `daydayup-game` 和 `daydayup-social` 服务中，设计数据库物理表结构，编写相应的 Entity、Mapper、Service、Controller，废除当前的 Mock 返回值。
- **优点**：能够完整落地持久化层，使得整个数据流更加闭环和真实。
- **缺点**：缺少对分布式锁、RocketMQ 消息队列、幂等机制等高端微服务特性的集成演练。

### 方案 B：纯粹的中间件能力整合（侧重组件，仍使用 Mock）
- **实现内容**：不引入真实表，仅在现有的 Mock Controller 上增加 `@OperLog`（日志）、`@Idempotent`（幂等）与 `@DistributedLock`（分布式锁）。在 `daydayup-common-mq` 基础上实现服务间 Mock 消息发送。
- **优点**：开发速度快，能直接验证切面组件、Redis 连接与 RocketMQ 链路。
- **缺点**：没有数据库持久化，属于“空中楼阁”，无法模拟真实的业务场景。

### 方案 C：混合场景落地（推荐方案）
- **实现内容**：挑选一个端到端的业务流程——**“玩家加入游戏房间与战绩动态分享”**，将数据库持久化与微服务高级能力进行一站式融合。
  1. **设计表结构**：在 `sql/` 下设计 `game_room`、`game_record` 与 `social_feed` 物理表。
  2. **幂等创建房间**：使用 `@Idempotent` 保证创建房间请求防重。
  3. **并发加锁进房**：使用 `@DistributedLock` 保证用户加入房间（满人限制）的并发安全。
  4. **领域事件异步化**：对局结束时，`game` 服务通过 RocketMQ 发送游戏结束消息；`social` 服务作为消费者异步接收消息，在数据库中生成一条新的好友动态。
  5. **定时任务**：通过 XXL-JOB 每天定时清理过期空闲房间。
- **优点**：一次性把 MyBatis-Plus、Redis、Redisson锁、RocketMQ、XXL-JOB 全部串联验证，最能体现企业级微服务骨架的价值。
- **缺点**：需要设计少量表结构并编写对应的消息消费者，工作量略大。
